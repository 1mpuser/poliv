# Решения

Почему сделано так, а не проще. Перед тем как «упростить» что-то из этого списка — прочитать причину.

### 1. Логика статусов только на бэкенде, чистыми функциями
Требование ТЗ: `/summary` отдаёт всё предпосчитанным. Правила — в `summary.py` без БД и без
`datetime.now()` внутри, поэтому тестируются без базы и без подмены времени.

### 2. Норма полива у растения (`water_interval_days`)
В исходном ТЗ её не было, но без неё нельзя сказать «пора поливать»; в макете она есть.

### 3. Порог «скоро» — `notify_days_ahead` учётки, для пересадки — фиксированные 14 дней
Порог из макета. Для проверки горшка (интервал в месяцах) предупреждение за 1 день бессмысленно.

### 4. Общая лампа — `lamp_sessions.plant_id IS NULL`
Лампа может светить на несколько горшков. Её часы засчитываются всем растениям учётки, пересечения
со своей лампой объединяются (не 8 часов, а 6, если 8–12 и 10–14).

### 5. Уведомлений нет
В макете есть «Время уведомлений» и «Зимний режим». Push-инфраструктуры нет — время уведомлений
не делали; зимний режим заменён сезоном из ТЗ (`active`/`dormant`), влияющим на интервалы удобрений.

### 6. Удобрения без NPK и доз в стартовых данных
Цифры с этикетки не выдумываем — заполняются в настройках.

### 7. Удаление удобрения — `ON DELETE SET NULL` в подкормках
История подкормок важнее справочника; в ленте будет «удобрение удалено».

### 8. Сервисы `poliv-web` и алиас `poliv-api`, а не `frontend`/`backend`
На сервере `poliv-web` сидит в сети трекера, где уже есть `frontend` и `backend`. Docker DNS отдал бы
на эти имена оба контейнера, и трекер через раз попадал бы в поливалку. Проверено: имя `frontend`
в сети трекера резолвится только в трекер.

### 9. Одна точка входа: nginx во фронтенде проксирует `/api`
Внешнему прокси нужен ровно один upstream (`poliv-web:80`), локальный Caddy настроен так же — прод и
локалка совпадают.

### 10. Встроились в Caddy трекера, а не подняли свой
TCP 443 занят трекером, порт 80 — acme.sh для VPN, UDP 443 — hysteria. Свой Caddy на другом порту не
получил бы публичный сертификат (Let's Encrypt проверяет 80 или 443) и оставил бы порт в адресе.
Сертификат — TLS-ALPN через уже работающий 443.

### 11. Правка Caddyfile трекера — дописыванием `>>`, с `caddy validate` и бэкапом
Файл примонтирован bind-mount'ом: редактор или `sed -i`, создающий новый файл, оставил бы в
контейнере старую версию. Ошибка в конфиге уронила бы и трекер — поэтому проверка до reload и
автовосстановление.

### 12. Код на сервер — `git archive HEAD`, не `git clone`
Серверу не нужен доступ к GitHub; уезжает ровно закоммиченное состояние.

### 13. Секреты генерируются на сервере и не выводятся
`.env` создаёт скрипт деплоя; пароли учёток печатает CLI один раз. Агент (Claude) их не видит —
классификатор Claude Code блокирует чтение секретов, поэтому такие команды выполняет пользователь через `!`.

### 14. Мультиучётки как в трекере: регистрации нет, учётки выдаёт админ
Один владелец раздаёт доступы. Данные учёток изолированы; чужое — 404, а не 403, чтобы не раскрывать,
что запись существует. Админка для не-админа тоже 404.

### 15. Отзыв токенов через `token_version`, а не таблицу сессий
JWT без состояния, но с версией учётки: смена пароля или блокировка увеличивают версию — все старые
токены сразу недействительны. Одна колонка вместо хранилища сессий.

### 16. scrypt из стандартной библиотеки
Без внешних зависимостей для хэширования; параметры (N=2¹⁴, ~16 МБ) рассчитаны на 1 vCPU / 2 ГБ.

### 17. Миграция 0002 отдаёт старые данные заглушке `owner@localhost.invalid`
Миграция не знает почту владельца. Заглушка — админ без пароля (войти нельзя), `set-owner`
превращает её в настоящую учётку, не перенося данные.

### 18. Тесты API на настоящем Postgres
Изоляция держится на SQL-фильтрах, частичных индексах и каскадах — SQLite это не проверит.
База для тестов обязана содержать «test» в имени — защита от стирания рабочей.

### 19. Естественный свет — солнечные часы Open-Meteo с учётом облачности
Выбор владельца: в пасмурный день досветка должна работать дольше. Open-Meteo бесплатный и без ключа,
город ищется по названию. Световой день (восход–закат) показывается справочно. Свет на подоконнике меньше
уличного — это грубая модель, норму можно ставить с запасом.

### 20. Норма — всего света, а не только лампы
`lamp_hours_per_day` переименован в `light_target_hours` (миграция 0003, значения сохранены):
в норму входят солнце и лампа. Норма — на растение, город — на учётку, расписание — на лампу
(своя у растения и общая).

### 21. Расписание розетки превращается в обычные сессии лампы
Розетка программируемая, не умная — приложение знает расписание, но не управляет. Фоновая задача
создаёт сессии по расписанию на сегодня; вся существующая логика (часы, графики, история, отмена)
работает без изменений, а смена расписания не переписывает прошлые дни. Через полночь — двумя интервалами.

### 22. Бэкап базы перед каждой выкаткой
`deploy-server.sh` снимает `predeploy-*.dump` (последние 10) до `up --build`: любая версия может принести миграцию.

### 23. Лампа — объект, растение под ней — период привязки
Несколько ламп на учётку, растение под одной. Часы растения считаются по лампе, под которой оно стояло тогда
(`plant_lamps`), удаление лампы — архив. Иначе перенос растения или удаление лампы переписывали бы прошлые недели.

### 24. Досветка — по самому требовательному растению, поровну утро/вечер
Одна лампа на несколько растений: горит, пока норму не наберёт самое требовательное (цитрусам лишний свет не вредит).
Утро планируется по прогнозу, вечер пересчитывается до заката по факту — ошибки прогноза компенсируются. Границы
06:00/23:00 — у лампы.

### 25. Розетка — через Умный дом Яндекса, команда только при смене состояния
Сервер на VPS, розетка Tuya облачная: Tuya Cloud требует продлевать пробный пакет, вход по QR Smart Life работает под
чужим client id. Яндекс — один OAuth-токен на год, любая розетка, видимая Алисе. Команда уходит только когда нужное
состояние меняется: ручное выключение через Алису не перебивается каждую минуту. Токен шифруется ключом из JWT_SECRET.
